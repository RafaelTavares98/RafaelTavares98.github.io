SQL: Fundamental Exploratory Data Analysis

A handful of commands answers most of what a business asks. Each one here ends in a decision.

A small set of commands, most of the work!

A fifth of SQL carries most of the work, and the same short list keeps coming up. Here it is.

  • SELECT / FROM
  • WHERE
  • DISTINCT
  • JOIN
  • GROUP BY
  • HAVING
  • SUM, COUNT, AVG
  • MIN, MAX
  • ORDER BY
  • LIMIT
  • UNION ALL
  • CASE WHEN
  • CTE (WITH)
  • Window functions
  • Subqueries
  • Date functions
  • COALESCE, NULLIF

The list is short for a reason. SQL rests on a small, closed set of operations, and business questions come in a narrow shape: how much, of what kind, compared to what, and which are the extremes. A short vocabulary is enough because the questions repeat. The hard part was never the syntax. It is knowing which item to reach for, and what the answer means once it arrives.

The data, and what is being checked

The warehouse is the teaching data set from Data With Baraa, written for SQL Server. I rebuilt the schema and rewrote every query for PostgreSQL 17.

It is a bicycle retailer in a star schema: 60,398 order lines, 18,484 customers, 295 products, from 2010 to 2014.

Exploratory analysis follows a fixed order:

  1. Read the structure, and find what one row means.
  2. Check the quality: nulls, duplicates, impossible ranges, broken keys.
  3. Look at one field at a time.
  4. Look at fields together.
  5. Look at the whole thing over time.
  6. Split it by segment and compare.

What it produces is not a conclusion. It is a shorter list of questions worth asking, and a note on what the data cannot answer. The five sections below work through that order.

Aggregates and UNION ALL: what is the current baseline?

The first question in any review is the size of the business. Five aggregates give it, and UNION ALL stacks them into a single result set instead of five separate queries. This is the shape of a KPI board before any tool draws it.

Query

SELECT 'Total Sales' AS measure_name, SUM(sales_amount) AS measure_value FROM gold.fact_sales
UNION ALL SELECT 'Total Quantity', SUM(quantity) FROM gold.fact_sales
UNION ALL SELECT 'Total Orders', COUNT(DISTINCT order_number) FROM gold.fact_sales
UNION ALL SELECT 'Total Customers', COUNT(customer_key) FROM gold.dim_customers;

The business turns over $29.36M across 27,659 orders, which puts the average order near $1,061. That single figure is the reference I check every later result against. A slice that implies an average order of $300 or $4,000 means the slice is wrong, not the business.

JOIN and GROUP BY: where does the revenue come from?

The fact table holds the money and the dimension table holds the labels, so one LEFT JOIN connects them and one GROUP BY collapses the result to the level the business thinks in. This pair is the most used construction in analytical SQL, and it answers the question that follows the totals every time.

Query

SELECT
    p.category,
    SUM(f.sales_amount) AS total_revenue
FROM gold.fact_sales f
LEFT JOIN gold.dim_products p ON p.product_key = f.product_key
GROUP BY p.category
ORDER BY total_revenue DESC;

Bikes produce 96.5% of the revenue. Accessories and Clothing together account for the remaining 3.5%, even though they hold most of the catalogue. This is concentration risk, and it is the kind of finding that changes a roadmap: a weak quarter for one category becomes a weak quarter for the whole company. The next query is the same one cut by margin instead of revenue.

DATE_TRUNC: is the business growing, and how steadily?

Dates are the field where SQL dialects differ most, and where a lot of analysts stall. In PostgreSQL, DATE_TRUNC flattens a timestamp to the start of the year, the month, or the day, which turns a raw order date into a reporting period. One function replaces the calendar table that this task often gets built with.

Query

SELECT
    DATE_TRUNC('year', order_date) AS order_year,
    SUM(sales_amount) AS total_sales,
    COUNT(DISTINCT customer_key) AS total_customers
FROM gold.fact_sales
WHERE order_date IS NOT NULL
GROUP BY DATE_TRUNC('year', order_date)
ORDER BY order_year;

Sales fell 17% in 2012 against 2011, then came close to tripling in 2013. A trend that moves like this is not a trend yet. Before anyone builds a forecast on 2013, somebody has to name the operational change behind it, whether that was a new product line, a new region, or a price move. The number is the symptom, and the change is the thing the business can repeat.

ORDER BY and LIMIT: which customers carry the revenue?

Ranking is the cheapest useful query in SQL, and it settles a question that changes how a retention programme is designed. If a handful of accounts carry the revenue, the company protects those accounts by name. If the revenue is spread, it needs a programme instead of a phone call.

Query

SELECT
    c.customer_key,
    c.first_name,
    c.last_name,
    SUM(f.sales_amount) AS total_revenue
FROM gold.fact_sales f
LEFT JOIN gold.dim_customers c ON c.customer_key = f.customer_key
GROUP BY c.customer_key, c.first_name, c.last_name
ORDER BY total_revenue DESC
LIMIT 10;

The ten largest customers each spend close to $13,000, and the gap between first and tenth is small. No single account dominates, so losing one of them costs the business little. The same result rules out a VIP list as a retention plan, because there is no meaningful VIP tier to build one from.

CASE and a CTE: what does the customer base look like?

CASE is how business rules enter SQL. It turns two continuous measures, how long a customer has been buying and how much they have spent, into the three groups a marketing team can actually work with. The CTE holds the per-customer totals so the CASE has something to classify, which is the only reason it is there.

Query

WITH customer_spending AS (
    SELECT
        c.customer_key,
        SUM(f.sales_amount) AS total_spending,
        (EXTRACT(YEAR FROM MAX(order_date)) - EXTRACT(YEAR FROM MIN(order_date))) * 12
            + (EXTRACT(MONTH FROM MAX(order_date)) - EXTRACT(MONTH FROM MIN(order_date))) AS lifespan
    FROM gold.fact_sales f
    LEFT JOIN gold.dim_customers c ON f.customer_key = c.customer_key
    GROUP BY c.customer_key
)
SELECT
    CASE
        WHEN lifespan >= 12 AND total_spending > 5000 THEN 'VIP'
        WHEN lifespan >= 12 AND total_spending <= 5000 THEN 'Regular'
        ELSE 'New'
    END AS customer_segment,
    COUNT(customer_key) AS total_customers
FROM customer_spending
GROUP BY customer_segment
ORDER BY total_customers DESC;

79% of the customers fall into "New", with less than twelve months of history. That figure has two readings and the data here cannot separate them: either acquisition is strong, or customers stop buying before the first year is out. The honest next step is a cohort retention check, not another acquisition metric on the dashboard.

Bottom line

Five commands and one date function carried this analysis from an empty console to three findings a manager can act on: the revenue sits in one category, the customer base has no anchor accounts, and four out of five customers are too new to judge. None of that needed a tool beyond PostgreSQL, and none of it needed SQL that a first-year analyst has not already seen.

What the fundamentals do not give you is the next step. Confirming whether 2013 was durable, or whether those new customers stay, needs window functions and cohort logic. That is the follow-up project, and it starts exactly where this one stops.
